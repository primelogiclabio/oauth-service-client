# Progress

Goal: Java library that makes outbound calls to OAuth-protected external services (e.g. DocuSign, Salesforce, Jira, Vertex payroll, Entra ID apps, Okta apps, Auth0, Oracle Integration (OIC)) for backend code: the caller passes client info (per service and tenant, or global) and the endpoint and payload; the library gets the token, cached per (service, tenant, user, scopes) until shortly before it expires, and makes the request. Basic first (token requests, public API, outbound requests, tests, README), then features on top.

## Decisions
- The library gets the token and makes the outbound request, the caller supplying only client info, a full-URL endpoint and payload, because config belongs to the service and tenant; AutoCloseable (initialize, calls, close) for try-with-resources; every HTTP answer, any status, goes back, and only failures without an answer (connection, timeout, TLS, getting the token) throw; a caller's own token (post(token, url, json), ServiceRequest.token) is used as is, with nothing of the ClientInfo (no client certificate, no allowed-host check): no cache, a 401 goes back to the caller
- Cache key is (service type, tenant, user, scope set), because some integrations are per tenant (DocuSign) and some shared (Salesforce), and tokens for different scopes must not replace each other; the user is the subject of a JWT bearer or refresh token grant (required for refresh tokens, never sent), so one user never gets another's token, and client credentials have none, since their token serves the whole tenant server to server; global is a flag (getTenant() null, isGlobal()), not a "GLOBAL" tenant string, so a real tenant coded GLOBAL can't collide; the app may pass scopes per request, replacing ClientInfo's defaults for that token, because often only the app knows them; a cached token is reused only while the settings that shape it match (token URL, grant, client ID, subject, audience, claims, scopes, parameters, client certificate), and rotated secrets, keys and refresh tokens keep it
- Java 8 and 21, the user's requirement (same as oauth-connector), so HTTP needs its own overall deadline code; the token cache is Caffeine (each token needs its own expiry, Guava has one per cache): 3.x in the Java 21 flavor (X.Y.Z), 2.9.x in the Java 8 flavor (X.Y.Z-jdk8, -Pjdk8), because Caffeine 3 needs Java 11; new project io.primelogiclab:oauth-service-client (package io.primelogiclab.oauthclient, next to oauth-connector's io.primelogiclab.oauth without sharing it) instead of slimming oauth-connector, because that one grew sign-in, multi-tenant IdP settings and msal4j this goal doesn't need; PATCH goes through java.net.http on Java 11+ (Java11PatchTransport in src/main/java11, compiled with release 11 by a JDK 11+ profile, loaded by name only when java.net.http exists), under the same TLS, certificate, deadline, size and redirect rules; no authenticator on that client, because with one a 401 becomes an exception, so PATCH can't use a proxy that asks for a login; on Java 8 ServiceRequest.patch fails with a clear error; host-name checks set on the client itself (sslParameters), library daemon threads, refused when jdk.httpclient.enableAllMethodRetry=true or a SOCKS proxy is configured
- The core stays generic: it implements the standards (RFC 6749, 7523, 8705) and common practice, and vendor differences go through generic settings (tokenParameter, assertionAudience, assertionClaim, clientSecretInBody); vendor features ship as add-on libraries on top of the base client, laid out like mailroom (parent POM, core, one add-on per vendor: oauth-service-client-docusign, -vertex, -oic), so the core isn't overcomplicated (the user's call, 2026-11-22); the Java 8 flavor keeps its -jdk8 version suffix (X.Y.Z and X.Y.Z-jdk8 of one artifact, add-ons too) rather than mailroom's -java8/-java21 artifacts, because 1.0.0 shipped that way and users then only bump the version (the user's call, 2026-11-27); still open: separate repos or modules
- ClientKey (key, optional chain, optional kid) serves as signingKey (JWT bearer assertion or private_key_jwt) or clientCertificate (mutual TLS), because "certificate instead of secret" means private_key_jwt at Entra/Okta and mTLS elsewhere; PEM input kept (PemKeys copied), because vendors hand out PEM and the JDK can't read PKCS#1 (DocuSign's format); the JWS algorithm is a ClientInfo setting (signingAlgorithm, JWS names), not on ClientKey, because it's the token server's preference and one key may serve servers that want different ones (Entra PS256, OIC RS256); it counts as a credential, not a token setting, and isn't picked from the metadata
- Client authentication follows from what's set: signing key outside JWT bearer = private_key_jwt, else secret (HTTP Basic header by default, because it's RFC 6749's must-support method, Okta's default and OIC's only form; body with clientSecretInBody(true), as Atlassian wants), else certificate alone = mTLS, else none; JWT bearer without client authentication sends only grant_type and assertion (no client_id), as DocuSign and Salesforce document; Extra JWT claims are caller-set strings (assertionClaim), because DocuSign wants scope inside the assertion; iss, sub, aud, exp, iat, nbf, jti stay library-set; attributes (caller data, never sent) are separate from tokenParameters (sent; reserved names like grant_type, scope rejected)
- Token expiry: JWT exp first (moved back when iat shows the token server's clock ahead; a past iat is left alone, as a server may hand out an earlier token), then expires_in, then introspection (RFC 7662); no guessed lifetime, a token with none is kept until a 401, because the JWT's exp is what the service checks; Renew 5 minutes before expiry (at half the lifetime for tokens under 10 minutes), so a nearly expired token isn't sent and the call made twice; one renewal per key through a map of in-flight futures, not Caffeine's compute, which would block other keys during a slow token request; waiters share the result or failure, except an interrupted renewal's; token requests are resent only when the server certainly didn't process them (no connection, 429, 503 with Retry-After; at most 2 retries in one 60 s deadline), because of vendor caps (Vertex) and rotating refresh tokens; every token request is also sent not resendable by the JDK (a 401 then reads as invalid_client); a failed TLS handshake is never retried, as it fails the same way again; after a failure the cache waits before the next one (5 s doubling to maxTokenRetryDelay, at least Retry-After), per cache key and only for the same token settings and credentials (a SHA-256 fingerprint, never the values), because a failure that won't fix itself would use up those caps while a config fix must work at once; only an OAuthServiceException from the fetcher counts, not an interruption; the ceiling isn't a token setting
- Metadata discovery: tokenUrl, or issuer and/or metadataUrl, never both; the document must name the configured issuer exactly (RFC 8414 3.3), so it can't send the client's credentials elsewhere under another name; kept a day per document for the JVM, with the copy held used when a refresh fails, because a metadata outage mustn't stop token requests; of the listed auth methods only Basic and body are swapped, since other mismatches are the caller's configuration; a failed read is a failed token request, so the cool-down applies
- Public API is get/post/put/delete shortcuts (each also with the caller's token) plus request(ServiceRequest) for other methods, headers and scopes, because real calls need PUT/DELETE, vendor headers and per-call scopes; ServiceResponse keeps the body as bytes with text on request (DocuSign PDFs), up to 16 MB; failures without a usable answer throw OAuthServiceException (public, unchecked; OAuth error, description, URI and HTTP status, -1 when none); HTTP plumbing stays package-private; for 1.0 introspectionUrl stays package-private until introspection is built (adding it later breaks no one), and so does OAuthServiceException's constructor with OAuth error fields (only the library knows them); every doclint warning fails the build, so the javadoc stays complete; javadoc covers src/main/java only (the Java 11 PATCH transport is package-private), while the sources jar has src/main/java11 too
- Service calls are resent by default only when nothing was sent or the service answers 429/503 with Retry-After (seconds or a date, at most 30 s, within the call's deadline); ServiceRequest.retryOnFailure() adds 5xx, busy answers without Retry-After and failures after sending, for idempotent calls; a 401 to the library's token renews it once (TokenCache.renew) and resends once within the same deadline, only if the token is at least 60 s old (else a permission 401 would spend vendor token caps); a Retry-After over 30 s or unreadable returns the answer; only RequestNotSentException counts as not sent; OAuthServiceClient.builder() sets connect/read/call timeouts (also for the instance's token requests, which keep 2 retries), retries 0 to 10 and maxResponseBytes; ServiceRequest.timeout sets one call's; clients with the same settings share their components (up to 16 settings); https only, no loopback exception (tests use an HTTPS stub with the test CA); a service call's URL is checked before a token is fetched; ServiceRequest refuses Authorization and the headers the JDK sets; a POST is sent not resendable, so the JDK never sends it twice (the body of a 401 to a POST is then unreadable); the client certificate goes on API calls too (certificate-bound tokens); the token cache is static per class loader, so it outlives close()
- Connections are kept alive by the JDK's pool, per host and TLS socket factory (one per client certificate, so a tenant's certificate connection carries no other call), service POSTs included (the user's call, 2026-11-22: a POST meeting a connection the server closes just then fails as sent, resent only with retryOnFailure); token requests get a connection of their own, because vendor caps and rotating refresh tokens make a lost one costly; every TCP socket under TLS is a TrackedSocket marking the request that last read or wrote it, because the JDK pools a connection inside read() and a late deadline must not close it under the next request; no library setting, http.keepAlive=false turns it off JVM-wide
- Requests in flight per host:port: one JVM-wide count for every client, tenant, token request and service call, set by the static OAuthServiceClient.setMaxRequestsPerHost (default 32), not a builder setting or per-tenant shares, because vendors limit per source and budgets per client or tenant would add up past that (the user's call, 2026-11-27); waiting calls first come, first served, with no fair hand-off between tenants, since that logic isn't worth its cost
- Security: own TLS context (the JVM's trust store, no javax.net.ssl.keyStore identity, HTTPS host name identification, a verifier that never makes exceptions), so JVM-wide defaults other code sets don't apply; the JVM's Authenticator answers only proxy logins (Java 9+); credentials a server echoes are replaced by ****; ClientInfo must come from trusted configuration, not tenant input; a JVM-wide CookieHandler gets a one-time warning, since HttpURLConnection can't opt out; allowed hosts are optional per ClientInfo (none: any https host), exact or *.domain (below it, not the domain itself, at least two labels), case-insensitive, any port; checked before a token is fetched for every call with the library's token; part of the token settings; no wildcard over an IP address; entries that may carry credentials aren't echoed; allowsHost refuses input that isn't a host
- Releases and signing: from 1.1.0 releases go to repo.primelogiclab.io (Reposilite: releases, snapshots) instead of Maven Central, the user's choice; 1.0.0 stays on Central only, because the same version must never be in two repositories; the tag workflow deploys with a token scoped to this artifact, and consumers add the repository (README); one OpenPGP key signs commits, tags and release files, a sign-only primary key with no subkeys, because Central (1.0.0) verifies only against the primary key; it expires 2028-11-14 so a lost key lapses on its own: renew a few weeks before (gpg --quick-set-expire, then keyservers, GitHub and the Bitwarden backup again); signing set in this repo's .git/config only, through Git for Windows' gpg

## Gotchas
- oauth-connector (../oauth-connector) is frozen and only a source of code to copy; don't change it from here
- .gitignore ignores *.key and *.p12 except src/test/resources/tls; regenerate those fixtures with its generate.sh (openssl + keytool), valid until 2036-11
- docs/services.md holds vendor facts checked 2026-11-14; recheck the linked vendor page before relying on a detail; Vertex Payroll's example expires_in is 1200 s, yet token requests are capped at 10 per 8 hours: check the real lifetime in a live call
- Keycloak live check: throwaway container oauth-service-client-it-keycloak (README); its JWT bearer grant needs --features=jwt-authorization-grant and a URL issuer, so that test client's ID is a URL
- HttpURLConnection: resends a buffered request once when the connection fails before the answer (fixed-length mode stops it, but then a 401 body is unreadable); asks the default Authenticator on a 401 challenge (setAuthenticator, Java 9+, stops it); disconnect() does nothing during the TCP connect (close the socket instead), and with a stream open closes some idle pooled connection of that host and factory, not its own; its keep-alive pool takes a connection back at the body's last byte, inside read(), and drains a half-read stream (up to 512 KB) in the background before pooling it; through an HTTP or SOCKS proxy the JDK makes the TCP socket itself (only TLS layering uses our factory); a POST takes a pooled connection only after a 1 ms open check; with TLS 1.3 a server refusing the client certificate does so after the handshake, so the client sees a write error, not an SSLHandshakeException
- Git for Windows' gpg (C:\software\Git\usr\bin\gpg.exe, 2.4.5) writes use-keyboxd into a new ~/.gnupg/common.conf but ships no keyboxd, so every key command fails (renamed to common.conf.bak); its passphrase prompt is a GnuPG window that may open behind others; in PowerShell 5.1 piping text into gpg (--import-ownertrust) fails with "colon missing", so use Git Bash
- main's ruleset protect-main (id 27331870) requires the 4 build checks by job name ("<flavor> on JDK <n> on <os>"): renaming or removing a job in build.yml leaves PRs waiting until the ruleset is updated; auto-merge is allowed, but GitHub won't turn it on for a PR whose checks already passed (merge that directly)
- JDK 8 runs use F:\java\java8 (8u501, has RSASSA-PSS; JAVA_HOME and PATH both); C:\Program Files\Java\jdk-1.8 holds no java.exe; switching between the Java 21 and Java 8 flavors needs clean (stale Java 21 test classes fail the JDK 8 run with "class file version 65.0"); RSASSA-PSS fails with "Parameters required" unless setParameter gets a PSSParameterSpec
- Release tags deploy with a Reposilite token (oauth-service-client-ci, rw on /releases/io/primelogiclab/oauth-service-client/) in the REPO_TOKEN_NAME/REPO_TOKEN_SECRET secrets, set 2026-11-27 and not yet used; Reposilite uploads aren't atomic and refuse redeploys, so delete a broken upload's files in the dashboard before re-running; 10 failed logins block the runner for 5 minutes
