# Progress

Goal: Java library that makes outbound calls to OAuth-protected external services (e.g. DocuSign, Salesforce, Jira, Vertex payroll, Entra ID apps, Okta apps, Auth0, Oracle Integration (OIC)) for backend code: the caller passes client info (per service and tenant, or global) and the endpoint and payload; the library gets the token, cached per (service, tenant, user, scopes) until shortly before it expires, and makes the request. Basic first (token requests, public API, outbound requests, tests, README), then features on top.

## Decisions
- The library gets the token and makes the outbound request, the caller supplying only client info, a full-URL endpoint and payload, because config belongs to the service and tenant; AutoCloseable (initialize, calls, close) for try-with-resources; every HTTP answer, any status, goes back, and only failures without an answer (connection, timeout, TLS, getting the token) throw; a caller's own token (post(token, url, json), ServiceRequest.token) is used as is: no cache, a 401 goes back to the caller
- Cache key is (service type, tenant, user, scope set), because some integrations are per tenant (DocuSign) and some shared (Salesforce), and tokens for different scopes must not replace each other; the user is the subject of a JWT bearer or refresh token grant (required for refresh tokens, never sent), so one user never gets another's token, and client credentials have none, since their token serves the whole tenant server to server; global is a flag (getTenant() null, isGlobal()), not a "GLOBAL" tenant string, so a real tenant coded GLOBAL can't collide; the app may pass scopes per request, replacing ClientInfo's defaults for that token, because often only the app knows them; a cached token is reused only while the settings that shape it match (token URL, grant, client ID, subject, audience, claims, scopes, parameters, client certificate), and rotated secrets, keys and refresh tokens keep it
- Java 8 and 21, the user's requirement (same as oauth-connector), so HTTP needs its own overall deadline code and the token cache uses Caffeine 2.9.x (each token needs its own expiry, Guava has one per cache, Caffeine 3 needs Java 11)
- New project io.primelogiclab:oauth-service-client (package io.primelogiclab.oauthclient, next to oauth-connector's io.primelogiclab.oauth without sharing it) instead of slimming oauth-connector, because that one grew sign-in, multi-tenant IdP settings and msal4j this goal doesn't need
- The core stays generic: it implements the standards (RFC 6749, 7523, 8705) and common practice, and vendor differences go through generic settings (tokenParameter, assertionAudience, assertionClaim, clientSecretInBody); vendor-specific clients are a separate layer on top, built later
- ClientKey (key, optional chain, optional kid) serves as signingKey (JWT bearer assertion or private_key_jwt) or clientCertificate (mutual TLS), because "certificate instead of secret" means private_key_jwt at Entra/Okta and mTLS elsewhere; PEM input kept (PemKeys copied), because vendors hand out PEM and the JDK can't read PKCS#1 (DocuSign's format)
- Client authentication follows from what's set: signing key outside JWT bearer = private_key_jwt, else secret (HTTP Basic header by default, because it's RFC 6749's must-support method, Okta's default and OIC's only form; body with clientSecretInBody(true), as Atlassian wants), else certificate alone = mTLS, else none; JWT bearer without client authentication sends only grant_type and assertion (no client_id), as DocuSign and Salesforce document; Extra JWT claims are caller-set strings (assertionClaim), because DocuSign wants scope inside the assertion; iss, sub, aud, exp, iat, nbf, jti stay library-set; attributes (caller data, never sent) are separate from tokenParameters (sent; reserved names like grant_type, scope rejected)
- Token expiry: JWT exp first (moved back when iat shows the token server's clock ahead; a past iat is left alone, as a server may hand out an earlier token), then expires_in, then introspection (RFC 7662); no guessed lifetime, a token with none is kept until a 401, because the JWT's exp is what the service checks; Renew 5 minutes before expiry (at half the lifetime for tokens under 10 minutes), so a nearly expired token isn't sent and the call made twice; one renewal per key through a map of in-flight futures, not Caffeine's compute, which would block other keys during a slow token request; waiters share the result or failure, except an interrupted renewal's
- Token requests are resent only when the server certainly didn't process them (no connection, 429, 503 with Retry-After; at most 2 retries in one 60 s deadline), because of vendor caps (Vertex) and rotating refresh tokens; every token request is also sent not resendable by the JDK (a 401 then reads as invalid_client); a failed TLS handshake is never retried, as it fails the same way again
- Public API is get/post/put/delete shortcuts (each also with the caller's token) plus request(ServiceRequest) for other methods, headers and scopes, because real calls need PUT/DELETE, vendor headers and per-call scopes; ServiceResponse keeps the body as bytes with text on request (DocuSign PDFs), up to 16 MB; failures without a usable answer throw OAuthServiceException (public, unchecked; OAuth error, description, URI and HTTP status, -1 when none); HTTP plumbing stays package-private
- Service calls are resent by default only when nothing was sent or the service answers 429/503 with Retry-After (seconds or a date, at most 30 s, within the call's deadline); ServiceRequest.retryOnFailure() adds 5xx, busy answers without Retry-After and failures after sending, for idempotent calls; a 401 to the library's token renews it once (TokenCache.renew) and resends once within the same deadline; OAuthServiceClient.builder() sets connect/read/call timeouts (also for the instance's token requests, which keep 2 retries), retries 0 to 10 and maxResponseBytes; ServiceRequest.timeout sets one call's; https only, no loopback exception (tests use an HTTPS stub with the test CA); a service call's URL is checked before a token is fetched; ServiceRequest refuses Authorization and the headers the JDK sets; a POST is sent not resendable, so the JDK never sends it twice (the body of a 401 to a POST is then unreadable); the client certificate goes on API calls too (certificate-bound tokens); the token cache is static per class loader, so it outlives close()
- Allowed hosts are optional per ClientInfo (none: any https host), exact or *.domain (below it, not the domain itself, at least two labels), case-insensitive, any port; checked before a token is fetched for every call carrying the ClientInfo's token or client certificate; not a token setting
- Security: own TLS context (the JVM's trust store, no javax.net.ssl.keyStore identity, HTTPS host name identification, a verifier that never makes exceptions), so JVM-wide defaults other code sets don't apply; the JVM's Authenticator answers only proxy logins (Java 9+); credentials a server echoes are replaced by ****; ClientInfo must come from trusted configuration, not tenant input

## Gotchas
- oauth-connector (../oauth-connector) is frozen and only a source of code to copy; don't change it from here
- .gitignore ignores *.key and *.p12 except src/test/resources/tls; regenerate those fixtures with its generate.sh (openssl + keytool), valid until 2036-11
- docs/services.md holds vendor facts checked 2026-11-14; recheck the linked vendor page before relying on a detail
- Vertex Payroll's example expires_in is 1200 s, yet token requests are capped at 10 per 8 hours: check the real lifetime in a live call
- Caffeine evicts variable-expiry entries in buckets of about a second: reads check expiry exactly, but size() can lag
- Keycloak live check: throwaway container oauth-service-client-it-keycloak (README); its JWT bearer grant needs --features=jwt-authorization-grant and a URL issuer, so that test client's ID is a URL
- HttpURLConnection: resends a buffered request once when the connection fails before the answer (fixed-length mode stops it, but then a 401 body is unreadable); asks the default Authenticator on a 401 challenge (setAuthenticator, Java 9+, stops it); disconnect() does nothing during the TCP connect (close the socket instead); With TLS 1.3 a server refusing the client certificate does so after the handshake, so the client sees a write error, not an SSLHandshakeException
